# Lesson 24: Failed First Mode — впалі спочатку

## 🎯 Learning Outcomes

Після цього уроку ви зможете:

- ✅ Розуміти `pytest --ff` (`--failed-first`) — спочатку впалі тести, ПОТІМ решта
- ✅ Відрізняти `--ff` від `--lf` (`--lf` лише впалі; `--ff` впалі першими + усі інші)
- ✅ Розуміти навіщо `--ff` потрібен: швидкий фідбек + повне покриття
- ✅ Поєднувати `--ff` з `-x` (перший впалий → стоп)
- ✅ Знати роль кешу `.pytest_cache` як джерела «хто впав»

---

## 📋 Передумови

Ви вже знаєте:
- `pytest --lf` — запуск лише останніх впалих тестів (Lesson 23)
- Як pytest зберігає результати в `.pytest_cache`

`--ff` — це «старший брат» `--lf`. Спочатку розберіться з `--lf`, а потім читайте цей урок.

---

## 📖 Теорія

### 1. `pytest --ff` — впалі спочатку, потім решта

Прапорець `--ff` (повна форма `--failed-first`) **не фільтрує** тести, а **перевпорядковує** їх: тести, які впали минулого разу, йдуть **ПЕРШИМИ** (у їхньому початковому порядку), а всі інші — **ПОТІМ**.

```bash
# спочатку прогнати повний набір (щоб кеш знав хто впав)
pytest

# наступний прогін: впалі йдуть першими, далі решта
pytest --ff
```

Порядок виконання після падіння `test_b`:

```
test_b   <-- впав минулого разу, тепер ПЕРШИЙ
test_a   <-- решта, у звичайному порядку
test_c
```

Ключова ідея: **жоден тест не пропускається**. `--ff` лише змінює черговість.

---

### 2. `--ff` vs `--lf` — головна відмінність

Обидва прапорці спираються на кеш минулого прогону, але роблять різне:

| | `--lf` (`--last-failed`) | `--ff` (`--failed-first`) |
|---|--------------------------|----------------------------|
| Що запускає | **ЛИШЕ** впалі минулого разу | **ВСІ** тести |
| Порядок | тільки впалі | впалі **першими**, далі решта |
| Пропускає passing | ✅ так (не запускає) | ❌ ні — запускає всі |
| Мета | максимально швидкий дебаг | швидкий сигнал + повне покриття |
| Час прогону | найкоротший | повний |

Коротко: `--lf` = «покажи мені тільки зламане», `--ff` = «зламане спочатку, але прожени взагалі все».

---

### 3. Навіщо `--ff` — фідбек і покриття разом

`--lf` економить час, але має ризик: ви бачите лише впалі тести й не помічаєте, що ваш фікс **зламав щось інше** (регресію).

`--ff` вирішує це:

- **Впалі йдуть першими** → ви одразу бачите, чи пофіксили те, що ламалось.
- **Далі йде решта** → повний набір проганяється, регресії не проходять повз.

Це особливо зручно у зв'язці з `-x`: перший впалий тест — той самий, який ви щойно чинили, тож зупинка на ньому дає миттєвий сигнал.

---

### 4. Кеш `.pytest_cache` — джерело «хто впав»

`--ff`, як і `--lf`, не «памʼятає» падіння сам по собі. Список впалих тестів зберігається у теці `.pytest_cache` (файл `lastfailed`) після кожного прогону.

```
.pytest_cache/
└── v/
    └── cache/
        └── lastfailed   <-- тут лежить хто впав минулого разу
```

Наслідки:

- Якщо **жодного прогону ще не було** — кеш порожній, і `--ff` виконає тести у звичайному порядку (перевпорядковувати нема що).
- Якщо кеш очистити (`--cache-clear` або видалити теку) — `--ff` знову не матиме що ставити першим.
- Прапорець `-p no:cacheprovider` **вимикає** кеш повністю — тоді `--ff` та `--lf` не працюють.

---

### 5. Комбінація `--ff -x`

`-x` зупиняє прогін на першому падінні. Разом із `--ff` це дає найшвидший цикл «фікс → перевірка»:

```bash
pytest --ff -x
```

Логіка:

1. `--ff` ставить раніше впалі тести **першими**.
2. `-x` зупиняється, щойно якийсь тест впаде.
3. Отже, якщо ваш фікс не спрацював — pytest впаде **одразу на першому ж тесті** й зупиниться, не витрачаючи час на решту.
4. Якщо ж усі раніше впалі тепер зелені — прогін піде далі по решті набору й перевірить регресії.

Це поєднання «швидко впасти там, де боляче» + «інакше — прогнати все».

---

### 6. `--ff` у роботі QA

- **Локальний дебаг великого набору** — хочете і швидкий сигнал по зламаному, і впевненість, що нічого не зламали далі.
- **Фікс регресії** — раніше впалі тести першими підтверджують фікс, решта — ловить побічні ефекти.
- **CI з довгим прогоном** — `--ff` не скорочує час, але ставить найважливіше на початок логів, тож проблему видно раніше.

Вибір простий: потрібен **лише** швидкий дебаг зламаного → `--lf`; потрібен швидкий сигнал **і** повне покриття → `--ff`.

## ⚠️ Типові помилки

### Плутати `--ff` і `--lf`

```bash
# ❌ Очікувати, що --ff запустить ЛИШЕ впалі
pytest --ff   # насправді запускає ВСІ, просто впалі першими

# ✅ Лише впалі — це --lf
pytest --lf
```

`--lf` фільтрує (тільки впалі). `--ff` перевпорядковує (впалі першими, але всі).

### Чекати сортування без попереднього прогону

```bash
# ❌ Перший прогін у чистій теці — кеш порожній, перевпорядкування не буде
pytest --ff   # виконає у звичайному порядку

# ✅ Спершу звичайний прогін наповнює кеш, потім --ff перевпорядковує
pytest
pytest --ff
```

### Думати, що `--ff` пропускає passing-тести

```
❌ «--ff швидший, бо не запускає зелені тести»
✅ --ff запускає ВСІ тести — час прогону повний; він лише міняє порядок
```

Швидшим прогін роблять `--lf` (менше тестів) або `-x` (рання зупинка), а не сам `--ff`.
