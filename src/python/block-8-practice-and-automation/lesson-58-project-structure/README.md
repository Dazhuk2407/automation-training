## 📖 Теорія

### 1. Навіщо потрібна структура

Коли проєкт складається з одного файла — усе просто. Але як тільки додаються десятки
тестів, сторінок, API-клієнтів і хелперів, без структури проєкт перетворюється на хаос.

Хороша структура дає:

- **Масштабованість** — легко додавати нові модулі без переписування старих.
- **Навігацію** — за назвою теки одразу зрозуміло, де що лежить.
- **Командну роботу** — усі дотримуються однакових правил, менше конфліктів у git.
- **Перевикористання** — хелпери й клієнти імпортуються, а не копіюються.

---

### 2. Типова розкладка

Мінімальний, але правильний Python-проєкт виглядає так:

```
my_project/
├── src/                    # весь робочий код застосунку
│   └── my_app/
│       ├── __init__.py     # робить теку пакетом
│       ├── main.py
│       └── utils.py
├── tests/                  # тести — ОКРЕМО від коду
│   ├── __init__.py
│   ├── conftest.py         # спільні фікстури pytest
│   └── test_main.py
├── requirements.txt        # залежності проєкту
├── README.md               # опис, як запускати
├── .gitignore              # що НЕ комітити (venv, .pyc, секрети)
└── pytest.ini              # конфігурація pytest
```

Замість `src/` невеликі проєкти часто кладуть пакет прямо в корінь:

```
my_project/
├── my_app/
│   ├── __init__.py
│   └── main.py
├── tests/
└── requirements.txt
```

---

### 3. Призначення ключових файлів

| Файл | Навіщо потрібен |
| --- | --- |
| `README.md` | Опис проєкту: що це, як встановити й запустити |
| `requirements.txt` | Список залежностей для `pip install -r` |
| `.gitignore` | Перелік того, що не потрапляє в git (`venv/`, `__pycache__/`, `.env`) |
| `pytest.ini` | Налаштування pytest (маркери, шляхи, опції) |
| `conftest.py` | Спільні фікстури та хуки для тестів (pytest підхоплює автоматично) |
| `__init__.py` | Позначає теку як Python-пакет, дозволяє імпорти |

---

### 4. Чому `tests/` тримають окремо

Тести — це **не** робочий код застосунку. Їх виносять у окрему теку `tests/`, щоб:

- код застосунку не «засмічувався» тестами;
- легко було запустити або виключити тести з пакування;
- структура тестів **дзеркалила** структуру коду.

```
src/my_app/api/client.py     →   tests/api/test_client.py
src/my_app/pages/login.py    →   tests/pages/test_login.py
```

`conftest.py` кладуть у `tests/` (або підтеки) — там описують спільні фікстури,
які pytest автоматично надає всім тестам поруч.

---

### 5. Структура QA-фреймворку

Для UI/API автоматизації використовують типовий поділ за відповідальністю:

```
framework/
├── pages/          # Page Objects — обгортки над сторінками UI
│   ├── login_page.py
│   └── home_page.py
├── api/            # API-клієнти (обгортки над HTTP-запитами)
│   └── users_client.py
├── helpers/        # утиліти: робота з датами, файлами, генерація даних
│   └── date_utils.py
├── data/           # тестові дані: JSON, фікстури, константи
│   └── users.json
├── tests/          # самі тести
│   ├── test_login.py
│   └── test_users_api.py
├── conftest.py
└── requirements.txt
```

- **`pages/`** — Page Object Model: кожна сторінка = клас із локаторами й діями.
- **`api/`** — клієнти для API, щоб тести не працювали з `requests` напряму.
- **`helpers/`** — дрібні перевикористовувані функції.
- **`data/`** — тестові дані, відокремлені від логіки.

---

### 6. Найменування

- Файли й теки — `snake_case`: `login_page.py`, `date_utils.py`, а не `LoginPage.py`.
- Тестові файли — з префіксом `test_`: `test_login.py` (pytest знаходить їх автоматично).
- Імена мають бути **зрозумілими**: `users_client.py`, а не `uc.py` чи `stuff.py`.

```python
# ❌ незрозуміло
# u.py, tmp2.py, misc.py

# ✅ зрозуміло
# users_client.py, login_page.py, date_utils.py
```

```python

```

### Тести впереміш із кодом

```
# ❌ src/my_app/login.py  та  src/my_app/test_login.py  поруч
# ✅ src/my_app/login.py  та  tests/test_login.py
```

### Коміт зайвого у git

```
# ❌ у репозиторії лежать venv/, __pycache__/, .env з паролями
# ✅ додати їх у .gitignore
```

### Відсутність README / requirements

```
# ❌ новий колега не розуміє, як запустити й що встановити
# ✅ README.md з інструкцією + requirements.txt із залежностями
```
