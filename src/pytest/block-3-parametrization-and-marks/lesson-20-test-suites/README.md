## 📖 Теорія

### 1. Що таке test suite

**Test suite** (набір тестів) — це логічно згрупована множина тестів, зібраних під конкретну мету.

Типові набори:
- **smoke** — швидка перевірка «чи взагалі система жива»
- **regression** — повна перевірка «чи ми нічого не зламали»
- **integration** — перевірка взаємодії компонентів

Набір — це не окремий файл чи клас. Це **спосіб вибрати** підмножину тестів із усього проєкту за спільною ознакою (найчастіше — за маркером).

```python
import pytest

@pytest.mark.smoke
def test_login_page_opens():
    ...

@pytest.mark.regression
def test_password_reset_email_expires_after_24h():
    ...
```

---

### 2. Smoke suite — швидко і про головне

**Smoke** — це невелика підмножина **критичних** тестів, які відповідають на питання: «чи працює основне?».

Ознаки хорошого smoke-набору:
- Мало тестів (десятки, не сотні)
- Швидко (секунди–хвилини)
- Тільки критичні шляхи: логін, головна сторінка, основний API-ендпоінт
- Запускається **часто** — на кожен коміт / деплой / PR

Мета smoke — швидко впіймати «система повністю зламана», не чекаючи повного прогону.

```python
@pytest.mark.smoke
def test_homepage_returns_200():
    assert get_status("/") == 200
```

---

### 3. Regression suite — повно і надійно

**Regression** — це **повний** набір тестів, який перевіряє, що нові зміни нічого не зламали в наявній поведінці.

Ознаки:
- Багато тестів (сотні–тисячі)
- Довше (хвилини–години)
- Покриває краєві випадки, рідкісні сценарії, старі баги
- Запускається **рідше** — уночі або перед релізом

Важливо: **smoke ⊂ regression**. Критичні тести входять і в smoke, і в regression. Тобто повний regression-прогін теж перевіряє те, що перевіряє smoke.

---

### 4. Реалізація через маркери

Найгнучкіший спосіб — позначати тести маркерами і запускати за `-m`.

```python
import pytest

@pytest.mark.smoke
@pytest.mark.regression
def test_login():
    """Критичний тест: входить і в smoke, і в regression."""
    ...

@pytest.mark.regression
def test_login_with_expired_token():
    """Краєвий випадок: тільки regression."""
    ...
```

Запуск наборів:

```bash
pytest -m smoke          # тільки smoke
pytest -m regression     # увесь regression (включно з критичними)
pytest -m "not smoke"    # усе, крім smoke
```

Маркери `smoke`, `regression`, `slow` вже зареєстровані глобально в `pytest.ini`.
Оскільки увімкнено `--strict-markers`, будь-який **власний** маркер треба зареєструвати
у `conftest.py` через `pytest_configure`, інакше pytest впаде з помилкою.

---

### 5. Структура: за теками АБО за маркерами

Є два основні підходи до організації наборів.

**Підхід А — за теками/файлами:**

```
tests/
  smoke/
    test_login.py
    test_homepage.py
  regression/
    test_login_edge_cases.py
    test_reports.py
```

Запуск: `pytest tests/smoke/`

**Підхід Б — за маркерами:**

```python
@pytest.mark.smoke
def test_login(): ...
```

Запуск: `pytest -m smoke`

| Критерій | За теками | За маркерами |
|----------|-----------|--------------|
| Тест у кількох наборах | ❌ дублювати файл | ✅ кілька маркерів |
| Наочність у файловій системі | ✅ видно одразу | ⚠️ треба читати код |
| Гнучкі комбінації (`smoke and not slow`) | ❌ | ✅ |
| Простота для новачка | ✅ | ⚠️ |

На практиці зазвичай **комбінують**: теки задають грубу структуру (unit / integration / e2e),
а маркери — перетини (smoke, slow, critical).

---

### 6. Робочий процес QA (smoke-then-regression)

Класична стратегія в CI:

1. **На кожен PR / коміт** → `pytest -m smoke`
   Швидкий фідбек. Якщо smoke червоний — далі можна не бігти.
2. **Уночі (nightly CI)** → `pytest -m regression`
   Повний прогін, коли ніхто не поспішає.
3. **Перед релізом** → `pytest` (усе) + ручні перевірки
   Максимальне покриття перед випуском.

Ідея: дешеві швидкі перевірки — часто; дорогі повні — рідше. Це економить час
розробників і ресурси CI, не втрачаючи покриття.

## ⚠️ Типові помилки

### Усе позначили як smoke

```python
# ❌ smoke перестає бути швидким
@pytest.mark.smoke
def test_generate_yearly_report_pdf():  # виконується 40 секунд
    ...

# ✅ важкий тест — у regression
@pytest.mark.regression
def test_generate_yearly_report_pdf():
    ...
```

Якщо в smoke потрапляє все — він втрачає сенс. Smoke має лишатися **швидким**.

### Тест без жодної категорії

```python
# ❌ Тест не входить у жоден набір — його не запустить ні -m smoke, ні -m regression
def test_important_thing():
    ...

# ✅ Явно віднесений до набору
@pytest.mark.regression
def test_important_thing():
    ...
```

Некатегоризований тест легко «загубити» — він не потрапить у цільові прогони.

### Дублювання замість smoke ⊂ regression

```python
# ❌ Той самий тест двічі — у smoke-файлі і в regression-файлі
# smoke/test_login.py    -> def test_login(): ...
# regression/test_login.py -> def test_login(): ...  (копія!)

# ✅ Один тест, два маркери
@pytest.mark.smoke
@pytest.mark.regression
def test_login():
    ...
```

Дублікати розходяться з часом і дають хибну впевненість. Критичний тест має бути
**один**, але належати обом наборам.
