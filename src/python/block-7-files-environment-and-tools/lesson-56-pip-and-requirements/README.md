## 📖 Теорія

### 1. Робочий цикл залежностей

Керування залежностями — це цикл, а не разова дія:

```
pip install X        →  додаємо потрібний пакет у venv
   ↓
розробка / тести     →  пишемо код і тести з цим пакетом
   ↓
pip freeze > requirements.txt   →  фіксуємо точні версії
   ↓
git commit requirements.txt     →  ділимося з командою / CI
   ↓
pip install -r requirements.txt →  колега / CI відтворює те саме середовище
```

Ключова ідея: `requirements.txt` — це **рецепт**, за яким будь-хто (людина або CI) відтворює
ідентичне середовище. Сам код парсингу цього файлу — звичайна робота з рядками, і саме її
ми практикуємо у прикладах (без реального `pip`).

---

### 2. Команди pip

Це команди **термінала** (не Python-код). Тут вони як довідка:

```bash
# встановити останню версію
pip install requests

# встановити конкретну версію
pip install requests==2.28.0

# встановити все з файлу
pip install -r requirements.txt

# оновити пакет до найновішої сумісної версії
pip install --upgrade requests

# видалити пакет
pip uninstall requests

# список встановлених пакетів
pip list

# детальна інформація про пакет
pip show requests
```

> ⚠️ У цьому уроці ми **не виконуємо** реальних `pip`-команд і не звертаємось до мережі.
> Приклади коду лише **парсять текст** `requirements.txt` як рядки.

---

### 3. Специфікатори версій

Специфікатор задає, **які** версії пакета допустимі:

| Специфікатор | Назва | Приклад | Значення |
|---|---|---|---|
| `==` | pinned (точно) | `pytest==7.4.0` | лише саме `7.4.0` |
| `>=` | minimum | `requests>=2.25.0` | `2.25.0` або новіша |
| `~=` | compatible | `flask~=1.4` | `>=1.4, <2.0` (сумісні оновлення) |
| `<` | upper bound | `numpy<2.0` | будь-яка версія до `2.0` |

Приклад `requirements.txt` зі змішаними специфікаторами:

```
pytest==7.4.0
requests>=2.25.0
flask~=1.4
numpy<2.0
```

`~=1.4` означає «будь-які оновлення, сумісні з `1.4`»: дозволяє `1.5`, `1.9`, але **не** `2.0`.

---

### 4. Формат requirements.txt

Правила формату:

- одна залежність на рядок;
- коментарі починаються з `#`;
- порожні рядки ігноруються;
- рядок = `ім'я` + `специфікатор` + `версія`.

```
# runtime-залежності тестового фреймворку
pytest==7.4.0
requests>=2.25.0

# інструмент репортів
allure-pytest==2.13.2
```

**Розділення runtime та dev.** Часто тримають два файли:

- `requirements.txt` — те, що потрібно для запуску тестів (pytest, requests, playwright);
- `requirements-dev.txt` — інструменти розробки (black, mypy, pip-audit).

Файл dev зазвичай підтягує основний:

```
# requirements-dev.txt
-r requirements.txt
black==24.3.0
mypy==1.9.0
```

---

### 5. Навіщо пінити версії

Пінінг (`==`) фіксує точну версію. У QA це критично:

- **Відтворюваність** — тести падають/проходять однаково на будь-якій машині й у CI;
- **Стабільність CI** — нова версія бібліотеки не «зламає» пайплайн несподівано;
- **Дебаг** — коли всі мають однакові версії, баг легше відтворити.

Без пінінгу CI може «зелений сьогодні, червоний завтра» — лише через тихе оновлення
транзитивної залежності.

---

### 6. Безпека залежностей (коротко)

- Не встановлюйте недовірені пакети (ризик typosquatting — `reqeusts` замість `requests`);
- Перевіряйте ліцензії (у пропрієтарних проєктах уникайте несумісних ліцензій);
- Скануйте залежності на вразливості інструментом `pip-audit`.

```bash
# перевірити встановлені пакети на відомі вразливості
pip-audit
```

---

### 7. Це у QA automation

Типовий `requirements.txt` тестового проєкту:

```
# тестовий фреймворк
pytest==7.4.0
pytest-xdist==3.5.0

# HTTP та API-тести
requests==2.31.0

# UI-автоматизація
playwright==1.42.0
```

Запінені версії гарантують, що вся команда й CI ганяють тести на однаковому стеку.

## ⚠️ Типові помилки

### Не пінити версії

```
# ❌ CI зламається, коли вийде несумісна версія
requests

# ✅ фіксуємо точну версію
requests==2.31.0
```

### freeze усього оточення зі «сміттям»

```bash
# ❌ pip freeze тягне ВСЕ, включно з транзитивними/локальними пакетами
pip freeze > requirements.txt

# ✅ фіксуємо лише прямі залежності вручну або через окремий інструмент,
#    а requirements.txt тримаємо чистим
```

### Плутати `==` і `=`

```
# ❌ невалідний специфікатор
pytest=7.4.0

# ✅ рівність версії — це подвійний ==
pytest==7.4.0
```

### Комітити venv замість requirements.txt

```
# ❌ .venv/ у git — величезний, платформозалежний, непотрібний
# ✅ у git комітимо requirements.txt, а .venv/ додаємо в .gitignore
```
