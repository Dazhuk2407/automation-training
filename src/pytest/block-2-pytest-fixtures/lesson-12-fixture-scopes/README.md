## 📖 Теорія

### 1. Що таке scope

**Scope** — це час життя одного екземпляра фікстури: скільки тестів використовують **той самий** результат, перш ніж pytest створить його заново.

За замовчуванням фікстура має scope `function`: pytest виконує її код **окремо для кожного тесту**. Але іноді setup дорогий (з'єднання з БД, запуск сервера, читання конфігу), і повторювати його для кожного тесту марно. Scope дозволяє сказати pytest: "створи це один раз і переви­користовуй".

```python
@pytest.fixture(scope="module")
def db_connection():
    conn = connect()      # виконається один раз на весь файл
    yield conn
    conn.close()
```

Ключова ідея: **scope керує тим, як часто виконується код фікстури**, а не тим, скільки тестів її бачать.

---

### 2. function (default): нова для кожного тесту

`scope="function"` — значення за замовчуванням. Фікстура створюється **заново перед кожним тестом** і знищується після нього.

```python
@pytest.fixture              # scope="function" неявно
def fresh_list():
    return []                # кожен тест отримує НОВИЙ порожній список
```

Це дає **максимальну ізоляцію**: тести не впливають один на одного, бо кожен працює зі своєю копією. Якщо один тест змінить дані — наступний тест цього не побачить.

Це найбезпечніший вибір і саме тому він за замовчуванням.

---

### 3. module, session, class: ширші scope

- **`class`** — одна фікстура на весь тест-клас. Спільна для всіх методів `test_*` усередині класу.
- **`module`** — одна фікстура на весь файл (`.py`). Спільна для всіх тестів у модулі.
- **`session`** — одна фікстура на **весь запуск pytest**. Створюється один раз і живе до кінця всіх тестів.

```python
@pytest.fixture(scope="session")
def app_config():
    return load_config("test.ini")   # один раз на весь запуск
```

Ієрархія від вужчого до ширшого:

```
function  →  class  →  module  →  session
(вужчий, більше ізоляції)   (ширший, більше переви­користання)
```

---

### 4. Синтаксис і скільки разів виконується setup

Scope задається аргументом `scope` у декораторі:

```python
@pytest.fixture(scope="module")
def shared():
    ...
```

Порахуймо, скільки разів виконається **setup** фікстури для **3 тестів** (в одному файлі, всі 3 в одному класі):

| Scope | Setup виконається | Пояснення |
|-------|-------------------|-----------|
| `function` | **3 рази** | по одному разу на кожен тест |
| `class` | **1 раз** | один раз на клас (всі 3 тести в ньому) |
| `module` | **1 раз** | один раз на файл |
| `session` | **1 раз** | один раз на весь запуск |

> Якщо ті самі 3 тести розкидані по 2 класах, `class`-фікстура виконає setup **2 рази** (по разу на клас), а `module` — все одно 1 раз.

---

### 5. Компроміс: переви­користання vs ізоляція

Вибір scope — це завжди компроміс:

| | Вужчий (`function`) | Ширший (`session`) |
|---|---|---|
| Швидкість | повільніше (багато setup) | швидше (setup один раз) |
| Ізоляція | максимальна | мінімальна — стан спільний |
| Ризик | низький | тести можуть впливати один на одного |

⚠️ Головна небезпека широкого scope — **спільний мутабельний стан**. Якщо `module`-фікстура повертає список чи словник, і один тест його змінює, наступний тест побачить **зміни**, бо це той самий об'єкт:

```python
@pytest.fixture(scope="module")
def cart():
    return []

def test_add(cart):
    cart.append("item")
    assert len(cart) == 1

def test_empty(cart):
    assert len(cart) == 0   # ❌ впаде! cart вже містить "item" з попереднього тесту
```

---

### 6. У QA: коли який scope

- **`session`** — дороге, незмінне на весь запуск: з'єднання з БД, запущений сервер/браузер-драйвер, завантажений конфіг, автентифікаційний токен.
- **`module`** — ресурс, спільний для групи пов'язаних тестів у файлі (наприклад, тестовий клієнт API).
- **`class`** — спільний контекст для методів одного тест-класу.
- **`function`** — **свіжі тест-дані**: об'єкти, які тести змінюють (тестовий користувач, кошик, тимчасовий файл).

Правило: **обирайте мінімальний scope, якого достатньо**. Ширший scope — лише коли setup справді дорогий, а дані не мутуються між тестами.

---

### 7. Зведена таблиця scope

| Scope | Час життя | Setup для 3 тестів | Коли використовувати |
|-------|-----------|--------------------|-----------------------|
| `function` (default) | один тест | 3 рази | свіжі мутабельні дані, максимальна ізоляція |
| `class` | один тест-клас | 1 раз/клас | спільний контекст методів класу |
| `module` | один файл | 1 раз | спільний ресурс для тестів файлу |
| `session` | весь запуск | 1 раз | дороге з'єднання/конфіг/сервер |

## ⚠️ Типові помилки

### Широкий scope + мутація спільного стану

```python
# ❌ module-фікстура з мутабельним списком — тести впливають один на одного
@pytest.fixture(scope="module")
def users():
    return []

def test_add(users):
    users.append("Alice")
    assert users == ["Alice"]

def test_fresh(users):
    assert users == []   # ❌ впаде — users вже ["Alice"]

# ✅ function scope дає свіжі дані кожному тесту
@pytest.fixture
def users():
    return []
```

### Думати, що module-фікстура «скидається» між тестами

```python
# ❌ Хибне очікування: "перед кожним тестом counter знову 0"
@pytest.fixture(scope="module")
def counter():
    return {"n": 0}
# module-фікстура створюється ОДИН раз — стан зберігається між тестами!
```

Module/session-фікстура **не** виконує setup заново перед кожним тестом. Якщо потрібні свіжі дані — це `function` scope.

### Надто широкий scope без потреби

```python
# ❌ session для даних, які тести змінюють — джерело "плаваючих" падінь
@pytest.fixture(scope="session")
def test_order():
    return {"items": []}

# ✅ Мінімальний достатній scope
@pytest.fixture
def test_order():
    return {"items": []}
```

Не робіть scope ширшим, ніж потрібно. Ширший scope економить час setup, але коштує ізоляції.
